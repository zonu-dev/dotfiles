# Goalプロンプト作成

## 概要

Codex TUIの `/goal` に渡すobjectiveを作成する。`/goal` は通常のシェルコマンドではなく、TUI内のスラッシュコマンドとして扱う。objectiveは最大4000文字なので、長い要件は `docs/goal.md` などのファイル参照に逃がす。詳細指示ファイルが必要な場合は、本文を提示するだけでなく実ファイルとして作成する。

## 手順

1. ユーザーが達成したい作業をヒアリングする。最低限、目的、対象リポジトリまたは作業ディレクトリ、完了条件、必須成果物、検証方法を確認する。
2. 足りない情報だけを短く質問する。質問は一度に多くしすぎない。明らかに推定できる内容は仮定として整理し、承認時に確認する。
3. 必要に応じて関連ファイルを読む。既存リポジトリ、設計文書、README、AGENTS.md、既存Web UI、既存Skill、過去提案などを参照する場合は、絶対パスまたは実行先から見た相対パスを明記する。
4. 生成前に、整理した情報をユーザーへ提示する。必ず次を含める。
   - 作業目的。
   - 実行場所と参照元。
   - 必須成果物。
   - 完了条件。
   - 検証コマンドまたは確認方法。
   - レビューや承認ゲート。
   - 未確定事項とこちらの仮定。
5. ユーザーに承認を求める。ユーザーが明確に承認するまでは `/goal` プロンプトを生成しない。
6. 承認後、貼り付け可能な `/goal ...` プロンプトを生成する。詳細ファイル方式が必要な場合、またはユーザーがファイル作成まで求めた場合は、`docs/goal.md` などの実ファイルを作成または更新してから `/goal ...` プロンプトを提示する。

## ヒアリング項目

必要な項目を状況に応じて確認する。

- `目的`: 何を最終的に達成したいか。
- `実行場所`: どのリポジトリ、ブランチ、作業ディレクトリで起動するか。
- `背景`: 空リポジトリでも伝わる前提説明が必要か。
- `参照元`: 参照すべき既存リポジトリ、ファイル、URL、提案、設計文書。
- `成果物`: 作成・更新すべきファイル、アプリ、ビルド成果物、レポート。
- `完了条件`: 数量、品質基準、LGTM条件、未解決指摘ゼロなど。
- `検証`: テスト、smoke、ビルド、ブラウザ確認、実機確認、レビュー方法。
- `権限範囲`: 変更してよい場所、触ってはいけない場所、参照専用のパス。
- `実行方針`: subagent、reviewer agent、WebSearch、ImageGen、Godot、Web UIなど必須ツール。
- `出力形式`: `/goal` だけか、詳細な `docs/goal.md` も必要か。
- `ファイル作成`: 詳細ファイル方式の場合に実ファイルを作成してよいか。ユーザーが明示的に求めた場合は作成まで行う。

## 整理提示フォーマット

承認前は、次の形式で提示する。

```markdown
以下の内容で `/goal` プロンプトを作ります。

- 目的:
- 実行場所:
- 参照元:
- 必須成果物:
- 完了条件:
- 検証方法:
- レビュー条件:
- 変更禁止/注意:
- 未確定事項:
- 仮定:

この内容で `/goal` プロンプトを生成してよいですか？
```

ユーザーが修正した場合は整理を更新し、再度承認を取る。

## 生成ルール

- `/goal` の本文は1行で貼れる形にする。
- 4000文字を超えそうな場合は、詳細指示を `docs/goal.md` に置く前提にし、承認後に `docs/goal.md` を実ファイルとして作成または更新してから、`/goal docs/goal.md の完了条件を満たすまで...` のような短いobjectiveを生成する。
- 詳細指示ファイルを作る場合は、`/goal` 側から解決できるパスを使い、ファイル本文にも完了条件、検証方法、レビューゲート、禁止事項を自足的に書く。
- 既存の詳細指示ファイルを更新する場合は、既存内容を確認し、ユーザーが明示していない無関係な内容を消さない。
- 空リポジトリや別リポジトリで実行する場合は、このリポジトリ固有の略称だけに頼らない。必要な背景をobjectiveに含める。
- 参照元が必要な場合は、実行先から見て解決できる絶対パスまたは相対パスを入れる。
- 完了条件は「作業する」ではなく「何が存在し、何が通り、何を確認済みなら完了か」で書く。
- 検証コマンド、レビューLGTM、レポート作成など、終了判定に必要なゲートを明示する。
- `update_goal` を呼ぶ条件は、すべての完了条件を実ファイル、コマンド結果、レビュー結果で監査できたときだけにする旨を含める。
- ユーザーが求めていない限り、こちらで `/goal` は実行しない。詳細指示ファイルが必要な場合はファイル作成まで行い、その後に貼り付け用プロンプトを出す。

## 出力フォーマット

承認後は、基本的に次の形で出力する。

```text
/goal ...
```

詳細ファイル方式が適切な場合は、承認後に実ファイルを作成または更新したうえで、作成済みファイルのパスと `/goal` を出す。本文をチャットに併記する場合は、実ファイルと同じ内容にする。

```markdown
# docs/goal.md
...
```

その場合、`/goal` 側には詳細ファイルを読むこと、完了条件を監査すること、完了時だけgoalをcompleteにすることを含める。
