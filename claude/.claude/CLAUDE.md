
## ファイル編集前のRead必須（厳守）

IMPORTANT: ファイルをEdit・Write・Updateする前に、必ずそのファイルをReadで読み込むこと。未読のファイルを編集しようとすると「File must be read first」エラーになる。推測や記憶に頼って未読ファイルを編集してはならない。

## Bashコマンド実行時の説明

Bashコマンドを実行する前に、コマンドとオプションの意味を日本語で説明すること。特に馴染みが薄いコマンドや複雑なオプションがある場合は、各オプションの役割を箇条書きで示す。

例:
```
`git log --oneline -5 --no-merges` を実行します。
- --oneline: 各コミットを1行で表示
- -5: 直近5件のみ
- --no-merges: マージコミットを除外
```

## 思考と意図の固定（厳守）

IMPORTANT: タスク着手前に「目的・方針・検証方法・既知のリスク」と「ユーザーが本当に知りたいこと / やってほしいこと」を言語化してから行動すること。表面的な単語ではなく、質問の焦点・完了条件・除外範囲を明示してから探索に入る。

以下の場合はプロンプト末尾に `ultrathink` 相当の深い思考を自ら課す:
- 3ステップ以上の手順を含むタスク
- 複数ファイルにまたがる修正
- 原因不明のバグ・失敗への対応
- アーキテクチャや設計判断を伴う変更

特に以下を厳守:
- 「これは何？」ではなく「なぜそうなった？」を問われた場合: 定義説明ではなく原因差分を答える
- 「修正して」「消して」「PR作って」ではなく、対象範囲が複数あり得る場合: 何をどこまでやれば完了かを先に固定する
- 文体・フォーマット指定がある場合: 内容生成前に完成形の型を固定する

「すぐ実行」は品質低下の典型パターン。仮説→検証→実行の順を崩さない。意図が曖昧なまま探索を始めると、調査量が増えても精度は上がらない。

## 前提条件とスコープの確認（厳守）

IMPORTANT: 失敗しやすいタスクでは、実作業の前に必要な前提条件と対象スコープを確認する:
- Git操作: `git status` / 対象ブランチ / 変更混在の有無 / どの差分が対象か
- GitHub操作: 認証状態 / 対象 repo / issue・PR番号 / 必要スコープ
- スキル・プラグイン利用: 実際に有効な名前・配置を確認し、古いパスや記憶を信用しない
- 生成物や自動更新ファイルを扱う変更: どのコマンド・フローが生成したかを確認する
- 調査・説明・コミット・PR作成: `git diff` / `git log` / `git blame` で「いつ・どこで・なぜ変わったか」を確認する

「前提が満たされているはず」「たぶんこの差分だろう」で進めるのは禁止。確認できるものは先に確認し、関連しない未追跡・未ステージ変更を巻き込まない。

## 探索優先（Read/Glob/Grep を Bash より先に）

IMPORTANT: ファイル探索・検索は専用ツールを使う。Bashでの代替は禁止:
- ファイル名検索: **Glob**（`find` / `ls -R` 禁止）
- コンテンツ検索: **Grep**（Bashでの `grep`/`rg` 禁止）
- ファイル読み込み: **Read**（`cat`/`head`/`tail` 禁止）

タスク着手前に関連ファイルを最低3つは事前読み込みし、コンテキストを確保してから Edit/Bash に進む。同じファイルを短時間に繰り返し読むのはコンテキスト喪失のサイン。初回 Read の結果を保持し、2回目以降は差分確認のみ。

## 編集後の検証（必須）

IMPORTANT: Edit/Write の後は必ず以下のいずれかで検証し、検証なしで完了宣言しない:
- `git diff` で変更内容を確認
- プロジェクトのテストコマンドを実行
- 型チェック / lint を実行
- 対象箇所を Read で再確認

編集と検証をペアで扱う。ユーザーに「完了しました」と報告する前に、自分で検証した根拠を示す。

## タスク分解（3ステップ以上で TaskCreate 必須）

IMPORTANT: 3ステップ以上の手順を含むタスクでは TaskCreate でタスクリストを作成する:
- 開始時: すべてのサブタスクを登録
- 着手時: TaskUpdate で in_progress に
- 完了時: 即座に completed に（バッチ更新しない）
- ユーザーが複数要件を提示した場合: それぞれ個別タスクに分割

計画なく並列・直列に実行し始めるのは禁止。

## 並列ツール呼び出し

依存関係のない独立したツール呼び出しは、1メッセージ内で必ず並列実行する:
- 複数ファイルの Read
- 独立した複数の Grep/Glob
- 独立した複数の Bash（git status と git diff 等）

直列実行は前の結果が次の入力に必要な場合のみ。

## 根本原因分析

IMPORTANT: エラー・失敗に遭遇した場合の手順:
1. まず根本原因を特定する（ログ・`git log`/`git blame`・関連コード確認）
2. 同じコマンド・操作を再実行して様子を見るのは禁止
3. ワークアラウンドより根本修正を優先
4. 破壊的操作（`--no-verify`, `reset --hard`, `-f` 等）で検証を回避しない

「エラーが消えた」≠「問題が解決した」。原因の仮説と検証を明示してから次に進む。

## 出力形式の忠実性

IMPORTANT: ユーザーが文体・フォーマット・粒度を指定した場合、その指定は内容要件と同等に扱う:
- 指定されたスタイル（例: スレ形式、レビュー形式、箇条書き、テンプレート）を守る
- 指定されていない装飾や余計な前置きを足さない
- レポートや説明文は、要求された観点がすべて入っているかを提出前に点検する

内容が正しくても、形式がずれていれば未達成とみなす。
